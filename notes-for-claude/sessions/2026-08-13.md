# 2026-08-13 — the startup investigation, and two things I broke

## Read this first if you are picking up startup work

The answer, as far as it goes: **one `texture_prefetch` call from `obj_init_Create_0` is
about three quarters of the init room**, and what it decompresses is glyph atlases —
`font_chi` ~11 s, `font_jp` ~9.9 s, `font_kr` ~4.1 s, `font_cyr` ~1.6 s, `font_lat`
~1.0 s, while `default` (every sprite in the game) is 0 ms.

**The one open question**: skipping the prefetch entirely saves nothing measurable,
because pages decompress on first draw instead. Declining an atlas that is *never drawn*
should be different. That has not been measured. `[feature.font_atlases]` exists, is off,
and is waiting for exactly that experiment.

## How I wasted most of a day, so you don't

I labelled the two hot functions **"ogg/vorbis decode"** on circumstantial evidence: the
CRC-32 polynomial `0x04C11DB7` is Ogg's page checksum, and the image contains `OggS` and
`vorbis`. Both true, both irrelevant — those strings belong to the audio subsystem, which
never appears on the stack. The functions run under `texture_prefetch`.

I then reasoned *from that label* for hours: that startup was audio, that the fix was
streaming sounds, that `texturegroup_load("splash_screen")` was the expensive call
because it was the last statement in init and the cost was large. All of it was built on
a name I made up and never checked.

`for-the-developers/performance.md`, written in the very first session, had it right the
whole time: "`obj_init_Create_0` → `texture_prefetch` → page decode". I regressed a
correct finding into a wrong one and spent a day getting back.

**What actually settled it**: `trace = <substring>` in the profiler config, which prints
whole stacks for samples whose innermost frame matches. One stack ended a week of
inference. If you find yourself deducing a caller from inclusive percentages, stop and
capture a stack instead.

## Two things I broke on the player's machine

**The profiler crashed the game, twice.** Sampling suspends and resumes the game thread
at 1 ms, and that makes `obj_font_tex_control`'s load callback fire twice, so
`generate_fonts` (62 KB, no re-entry guard) raises "font already exists". Both times were
because a measuring configuration was left installed. The profiler now stops itself after
`stop_after_s`; `measure-startup.py` restores the config at the end of every run unless
`--keep`. **Do not use `--keep` outside a back-to-back batch.**

**I destroyed `profiler.rs`** with `io.open(path, 'w', newline='\\n')` — Python truncates
on open, then raised on the invalid argument. There was no version control at the time.
There is now: `git init`, pushed to `github.com/momom2/tkiw-mods` (private). Use Edit for
source, not Python one-liners; Edit cannot truncate a file on error.

## Tooling that exists now

| tool | what it answers |
|---|---|
| `measure-startup.py` | switch everything off, profile one launch, restore |
| `profiles.py` | median and 95% CI across all recorded runs |
| `timeit.py` | time-to-menu over N launches, median and spread |
| `builtin_calls.py` | which builtins a GML function calls, by name |
| `gen_builtin_table.py` | bakes 2,769 builtin names into the runtime |
| `slotrefs.py` | every reference to a GML variable, exhaustively |

The profiler writes one CSV per launch to `tkiw-momomod-kit/profiles/`. Twenty-two are
on disk. Delete them if you change what is measured.

## Numbers to distrust

Run-to-run spread on time-to-menu is **18.8 seconds** with nothing changed. Any startup
claim from a single launch is a hypothesis. Several in this repository were, and two of
them were wrong.
