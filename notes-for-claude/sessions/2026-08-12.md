# Overnight session, 2026-08-12 (00:35 – 06:00)

Unattended. What was asked for, what was delivered, and what was deliberately not
attempted — so the next session does not have to reconstruct the reasoning.

## Delivered

**The modkit.** One Cargo workspace; `cargo test --release` runs **75 tests** across
every mod. `tkiw-runtime` holds the shared layer and gained five modules tonight:
`modules` (enumeration + per-module unwind data), `sample` (thread suspension and
stack walking), `symbolize` (address → GML name), `patch` (verified, revertible byte
patching), `phase` (crash-report breadcrumb). `package.py` builds the shipping zip and
**refuses to package a DLL carrying a stamped path**.

**`fast_boot` — a measured ~30% cut in startup.** Four runs with, three without:

| | with | without |
|---|---|---|
| to the main menu | 23.1 / 24.3 / 26.8 / 27.7 s | 39.1 / 42.8 s |

Found by profiling, not guessing: 59% of the first fifteen seconds sat inside
`texture_prefetch`, called from `obj_init_Create_0`, doing CPU-bound texture decoding.
Neither hot function calls a Windows API, which ruled out the obvious 530 MB-`data.win`
theory. Details and the honest caveat — about 8 of the 18 seconds saved reappear during
the splash — are in [`FINDINGS.md`](FINDINGS.md).

**The profiler earns its place.** It gained module attribution and unwinding *through*
foreign modules, so a stack now runs from `ntdll` back into the game code that was
waiting; and it keeps a **second profile of only the samples taken while the game was
overdue to draw**, because an average profile of a hitching game is dominated by the
frames that were fine.

**The auto-picker shares the runtime.** Fourteen files and 2,273 duplicated lines no
longer compile; the nine baked addresses it carried are now `tkiw_runtime::guard::CORE`.
Behaviour, proxy slot, marker, config and log are unchanged, and a live launch confirmed
it: symbols resolved, all nine addresses verified, `pending_rewards` read back. Both
mods load together.

**`playtest.py`** launches the game unattended, watches a log, and kills it — which is
what made tonight possible at all. Two things it had to learn: running the exe directly
does not work (Steam relaunches and the original exits 0), and a force-kill leaves the
crash-loop breadcrumb behind, which silently makes the *next* launch passive.

## Not delivered, and why

**Production replacement, modified production values, unit stats on hover.** All three
put something new on screen and **the kit cannot draw**: its only foothold is the
message pump, reached after the frame is finished. The groundwork is in
[`gameplay-features.md`](gameplay-features.md) — objects, variables, the three routes
out, which each feature probably wants, and one false lead. The route that unlocks the
hardest of them is a code detour into a Draw event, and that should not be attempted by
someone who cannot see the screen: a wrong detour is a crash or a corrupted frame, and
neither shows up in a log.

**The main-menu lag spikes cannot be fixed here** — this is a finding, not a shortfall.
The stall profile contains no game code at all: `Present` blocking in the graphics stack
on integrated graphics, Steam overlay in the path. The useful advice is outside the mod.

**The in-run stutter with many units is unprofiled.** Measured (~3.4 stalls/second,
median 63 ms) but not attributed, because reaching a unit-heavy run needs a human at the
controls. Everything needed is in place: enable `profiler`, load the run, read the
stalled-samples block. This is the single highest-value thing a person can do next.

**A splash-screen skip was considered and dropped.** It would need a *write* into the
GML runtime, and stacking a second experimental startup intervention on top of
`fast_boot`, unsupervised, risked re-creating the startup hang that had already cost a
session.

## Corrections made to earlier conclusions

Three things previously recorded as fact turned out to be wrong. All are fixed at the
source, because a wrong note is worse than no note.

1. **"Compiled GML never calls the builtins."** Backed by a real measurement — zero
   direct call sites for every builtin checked — and the wrong inference. A live stack
   showed `texture_prefetch` being called through a dispatcher at `0x1aa46c0` that
   scales a function index by 24. "No direct call sites" is a fact about one instruction
   encoding, not about what the program does.
2. **`0x1aa46c0` was mislabelled** `RValue_from_literal`, guessed from nearby string
   constants. It is that dispatcher. The profile exposed it: nothing that builds a
   string from a literal calls `texture_prefetch`.
3. **The phase timeline mis-attributed startup.** It reported `obj_init` appearing at
   25.8 s; the profiler shows `obj_init_Create_0` running from ~3.5 s. A marker that
   depends on the game's own data structures cannot see anything before those structures
   exist — which is exactly the phase worth measuring.

## Bugs found in my own work

* **A diagnostic amplified a slow launch into a stopped game.** Registry lookups whose
  misses cannot be cached re-walked up to 2²⁰ buckets; at ~3 s per poll on the frame
  hook, the game never reached its menu. Fixed with a rate-limited shared snapshot —
  *and* with an absolute per-call ceiling in the loader, because the existing budget
  check was gated on "was the game pumping normally" and so was blind to the feature
  that made it abnormal.
* **A proxy returning 0 on failure.** Inherited from `version.dll`, where 0 means
  failure. Every `mfreadwrite.dll` export returns an `HRESULT`, where **0 is `S_OK`** —
  so it was telling the game a call had succeeded while writing nothing to the output
  pointer. Now `E_FAIL`.
* **A module list enumerated once** put 37% of a menu profile into `<unmapped>`, and
  lost the stacks behind those frames too. Re-enumerated every three seconds.
* **`Runtime::resolve` resolved the global container at startup**, which is before the
  game's entry point, where it is null — disabling the whole kit 0.37 s into the first
  launch it ever ran.
* **The crash-loop breadcrumb survived a clean stand-down**, which would have told the
  player their last session crashed when it had not, and cost them the next one.
